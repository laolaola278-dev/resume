写 AgentOS 时我给自己定了一条硬约束：**任何任务都不允许从"执行中"直接跳到"完成"**。

状态流转刻意做得不平滑：

```
VERIFYING → REVIEWING → 通过 → COMPLETED
                     ↘ 不通过 → pendingFailure → FIXING → 回到 VERIFYING
```

多出来的这一圈，是我从踩过的坑里换来的。早期版本里 Agent 跑完就直接标完成，结果它"完成"了一堆根本没跑通的任务——语法错的补丁、没装依赖的脚本、声称测过但测试压根没执行。日志看着很漂亮，实际全是空的。

加了审查环节之后，Agent 必须先交出**可验证的产物**：能跑的测试、能复现的命令、改了哪些文件，再由独立的 review 判断放行还是打回。

打回不是简单地失败重试，而是把任务推进 `FIXING` 态，带着"具体哪里没通过"回到执行。`pendingFailure` 这个中间态的作用，是让"没通过"成为一个**可以被观测、被统计、被追问的状态**，而不是一句埋在日志里的 error。

代价是慢。同一个任务，带审查的版本耗时明显更长。但我认为这个交换值得——在无人值守的自动化里，"完成了但其实是错的"比"没完成"危险得多，因为它会静默地污染后续所有判断。

这条约束后来也改变了我的习惯：现在评估任何一个 Agent 系统，我第一个问题不是"它能做什么"，而是"**它怎么证明自己做对了**"。
