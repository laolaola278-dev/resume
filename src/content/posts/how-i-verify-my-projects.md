我 GitHub 上有 31 个仓库。很长一段时间里，我以为数量本身就是说服力。

后来我意识到一件不太舒服的事：**如果我自己都说不清哪些真的跑过，那这些项目对别人就没有意义。**

于是我做了一件事：把每个项目的验证状态标出来。

## 三种状态，而不是一种

我给项目分了四类标签：
- **已实机运行验证** —— 我在真实环境里装过依赖、启动过、调用过接口，输出可以复现
- **项目自带真实截图** —— 截图由仓库里的自动化脚本从真实运行的 UI 捕获，不是我摆拍的
- **代码审计通过** —— 代码和文档完整、调用链自洽，但我没能在本环境跑起来
- **二次开发** —— 基于别人的开源项目改造，我会写明上游是谁、我改了什么

最后这一类是我特意加上去的。有个项目（Doubao WPlus）是基于开源项目 DeepSeek++ 改的，
上游作者贡献了 77 个提交，我做了 16 个。把它说成"独立开发"是不诚实的，
但藏着不提又会低估我实际做的事——**写清楚来源 + 写清楚我改了什么，才是对的**。

## 一个我差点删掉的数字

跑 crew-skill 的上岗考试时，我得到 **40/100，判定 not ready**。

而项目 README 里写的是 **67/100**。

那一瞬间我犹豫过：要不要换个仓库再跑一次，跑出个更接近 67 的数字？

我没有。我把 40 分原样记录了下来，并且写清楚了为什么低：
README 的 67 分测于一个 300-commit 的仓库，我用的是 16-commit 的仓库，
时间切分之后**训练窗口里一个 commit 都没有**，能蒸馏的素材本就少得多。

但真正让我决定保留这个数字的，是另一件事：

> 工具在素材不足的时候，诚实判了 `not ready`，没有为了好看去凑一个高分。

一个会主动承认"我还不行"的工具，比一个总能交出漂亮数字的工具更值得信任。
我的作品集也应该这样。

## 对照实验比成功案例更有用

做 AgentOS 的时候，我设计了一道闸门：任务只有在验证命令通过、独立评审 PASS 之后才算完成。

"设计了一道闸门"这句话很好写，但它跟**闸门真的管用**是两回事。

所以我做了一次对照实验：故意让验证命令指向一个永远不会被创建的文件。

结果：执行器写文件其实成功了，但验证失败，程序直接判 `FAILED` 并转 FIXING 让 debugger 诊断，
**根本没有进入评审阶段**。

如果我没做这次实验，我只能说"我设计了验证机制"；
做了之后，我可以说"我验证了它会拦住该拦的东西"。

这两句话的分量完全不同。

## 我也删掉了一些东西

清理仓库的时候，我发现自己 fork 过一个 429 stars 的项目（wmux），
我在里面只贡献了 1 个提交，其余 97 个都是原作者的。

那个项目我最后没有放进作品集，一个字都没提。

不是因为它不好——恰恰相反，它很好，好到我没法假装它是我的。

## 最后

标注验证状态这件事，短期看是给自己找麻烦：
你得承认有些项目没跑起来，得承认有些数字不好看，得承认有些东西是别人的。

但长期看，它替我回答了面试官最想问的那个问题——

**"这些里面，有哪些是你真的懂的？"**

我把答案提前写在了那里。
